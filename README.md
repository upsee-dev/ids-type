# IDS漢字入力

読めない漢字を、見たまま打てる。IDS（漢字の空間構造記述）コード＋部品で漢字を検索・入力する日本語キーボードプロジェクト。入力方式は [zi.tools](https://zi.tools/?secondary=ids) のIDS部品入力を日本語市場向けに再設計したもの。
企画立案：西岡佑都
アプリ制作＆企画伴走：春木俊明
2026.07

```
LR日月 → 明     UD宀子 → 字     OC囗玉 → 国     RU辶刀 → 辺
```

Web版・Expoアプリ・システムキーボード（Android IME / iOSキーボード拡張）の3つがあり、
検索エンジンと辞書は `core/` の1か所を共有している。

## 構成

```
├── core/                  # 依存なしの共有コア（Web版・アプリ版で同じものを使う）
│   ├── index.ts           #   公開API。web/native はこれだけ見る
│   ├── engine.ts          #   検索エンジン(構造マッチ・部品包含・一覧)
│   ├── ids/               #   かたちコード⇄IDC・字形の正規化・IDS構文解析
│   ├── data/              #   ブロック表・部品パレット・着せ替え・辞書の型
│   ├── ids/operators.ts   #   かたちの配置図（Kotlin/Swift へは build:data が生成）
│   ├── handwriting.ts     #   手書き検索の照合(パターンは build:handwriting が生成)
│   ├── data/kana.ts       #   読み入力の面(フリック/ローマ字/Godan・4実装で共有)
│   └── kanji-data.json    #   生成済み辞書(102,999字・5.5MB / gzip 1.6MB)
├── data-src/              # 元データ（加工しない。出典は sources.json）
├── web/                   # Webプロトタイプ (Next.js + React + Tailwind)
│   ├── src/app/           #   入力画面・収録漢字一覧(?q= と ?block= で共有できる)
│   └── scripts/           #   辞書ビルド・エンジンテスト
├── native/                # Expoネイティブアプリ (iOS / Android)
│   ├── App.tsx            #   コンテナーアプリの画面（設定・お試し入力）
│   ├── ime/               #   ★Androidシステムキーボード本体（Kotlin）
│   ├── targets/keyboard/  #   ★iOSキーボード拡張（Swift）
│   └── plugins/           #   prebuild後の android/ へ ime/ を注入する config plugin
├── scripts/               # フォント・アイコンの生成、ストア提出
└── docs/                  # 事業戦略・技術ロードマップ
```

エンジンと辞書は `core/` の1か所だけにある。Web版は相対パスで直接読み
（`web/next.config.ts` の `turbopack.root` をリポジトリ直下に設定）、
アプリ版はビルド時に `native/src/core/` へ複製して読む
（Metro がプロジェクト外を解決できないため）。

`core/` 内の相対 import には `.ts` を付けている。Turbopack・Metro・Node の
型ストリッピングのどれでも同じコードが動くようにするため。辞書ビルドが
`core/data/blocks.ts` を直接 import できるのはこの形のおかげで、
**ブロック表がビルドと実行時で二重管理にならない**（以前これがずれて、拡張C/Eの
末尾18字が黙って辞書から落ちていた）。

同じ理由で、**Kotlin と Swift のテーブルは手で書かず生成する**。
部品パレットと着せ替えは `core/` の定義から `build:data` が
`Palettes.{kt,swift}` `Themes.{kt,swift}` を、フォントの範囲表は
`build-font-app.py` が実際の収録字から `ExtFonts.{kt,swift}` を書き出す。

## 収録範囲（[zi.tools](https://zi.tools/?secondary=character_set) と同じ全CJK漢字）

**Unicode 18.0 が定義するCJK漢字 102,999字（統合漢字 101,985 + 互換漢字 1,014）を、過不足なく全部**収録している。UCD の `UnicodeData.txt` と突き合わせて収録もれ0字・余分0字を確認済み。

| ブロック  |   字数 |     | ブロック           |  字数 |
| --------- | -----: | --- | ------------------ | ----: |
| 基本(URO) | 20,992 |     | 拡張F              | 7,473 |
| 拡張A     |  6,592 |     | 拡張G              | 4,939 |
| 拡張B     | 42,720 |     | 拡張H              | 4,192 |
| 拡張C     |  4,160 |     | 拡張I              |   622 |
| 拡張D     |    223 |     | 拡張J              | 4,298 |
| 拡張E     |  5,774 |     | 互換漢字・互換補助 | 1,014 |

- **99.89%（102,883字）に分解データが付いている**。残る116字は、そもそも分解できない基本字（`一` `口` `女` `人` `乙` など）と、どの表にも分解が無い字（拡張Jの6字ほか）。候補としては収録されているが構造検索には出ない
- **1字につき分解は1つとは限らない**。13,896字は「別の分解」も持っている（下の「同じ字でも切り方は人による」）
- 収録漏れが出ないよう、`build:data` は毎回ブロックごとの収録数を検証し、1字でも欠けるとビルドを失敗させる（範囲表は `core/data/blocks.ts` の1か所）
- **拡張Dの末尾 `𫠞`（U+2B81E・⿰日欠）は Unicode 18.0 で増えた1字**。18.0 の統合漢字の追加はこれだけで、上流のIDS表（BabelStone 16.0 / CHISE 17.0）がまだ持っていないため、分解だけ `web/scripts/build-data/supplement.mts` で補っている（画数8は Unihan 18.0 に入った）。上流が追いつけばそちらが優先されるので、追いついた時点でこのファイルを消せる

### 同じ字でも切り方は人による（分解を1つに決めない）

部品で漢字を引く道具なので、**打った組み合わせが辞書の分解と違うと引けない**のが
いちばん痛い。ところが「どう切るか」は表によって違う。

```
丟  ⿱王厶（CJKVI）   ／  ⿱一去（BabelStone）
亦  ⿱亠⿻⿰丿亅八     ／  ⿱亠④（④＝Unicode に無い部品にCJKVIが振った仮番号）
```

そこで **1字につき「主の分解」＋「別の分解」を最大2つ**持ち、
**どれか1つに当たれば引ける**ようにしてある（`merge.mts` が3つのIDS表から集め、
部品の集合が主と違うものだけを控える）。13,896字が別の分解を持つ。
効き方は3か所とも同じで、部品検索（閉包）・構造検索・完全一致の判定すべてに効く。

```
王厶      → 丟  （CJKVI の切り方で打った）
一去      → 丟  （BabelStone の切り方で打った）
UD王厶    → 丟      UD一去 → 丟   （かたちを付けても両方通る）
```

**穴あきの分解は主に選ばない**。CJKVI は Unicode に無い部品を①②③…で書く。
番号は字ごとの仮の名前で、同じ ⑤ でも 即(左)・其(上)・段(左) で形が違う。
そのまま入れると 不＝⿱一③ のように**誰も打てない部品**が混じって部品検索から漏れる。
別の表に穴の無い分解があればそれを主にする（354字）。

どの表にも穴の無い分解が無い字は、**BabelStone の私用領域の部品を使った分解**を主にする（406字）。
BabelStone は Unicode に無い部品を {18} のように番号で書き、ヘッダで番号ごとに
BabelStone Han PUA フォントの符号位置（{18}＝即の左 → U+F2B4）を示している。
その字を分解にそのまま入れ、同梱フォント `KatachiPUA`（部品121個ぶん・Web 18KB）で描くので、
⑤ や ？ ではなく実際の形が見える。CHISE の外字（&CDP-8B7C; など）も、同じ字の分解を
BabelStone と並べて対応を取り（87個）、同じ部品に寄せている（飠＝⿱亽＋即の左）。

```
即  ⿰⑤卩  →  ⿰[即の左]卩      鳥  ⿹⑦灬  →  ⿹[鳥の外側]灬
既 U+FA42（互換漢字）は統合漢字の 既 の分解を借りる
```

私用領域の部品は打てないので、検索での扱いは ①②③・？ と同じ。元の表の切り方に
しか無い部品で引けるよう、穴あきの分解は「別の分解」として残す（其＝⿱⿱⑤一八 の 一）。
KANJIDIC2 の13,108字で穴が残るのは 幺＝⿰②丶 だけ（BabelStone は分けない字とするが、
消すと 幺 を含む 胤 などが 丶 で引けなくなるので残す）。ほかに残るのは拡張漢字の
60字ほどで、CHISE にしか無い外字（BabelStone の部品表に対応が無いもの）を含む。

### 画数（10万字ぜんぶにある）

KANJIDIC2 の画数は13,108字ぶんしか無いので、拡張漢字を絞るのには使えなかった。
**Unihan 18.0 の `kTotalStrokes` は102,999字ぜんぶにある**ので、こちらを辞書に入れて
読みの検索と重ねて使う（KANJIDIC2 側に画数があればそちらを優先。画数の無い字 0）。
17.0 の Unihan には `𫠞`（U+2B81E）の行が無く、8画を `supplement.mts` で足していた
（Unihan 側が優先されるので、いまは控えとして残っているだけ）。

「こう」と打つと4,634字当たるが、6画で絞ると110字になる。画数はその場で数えられる
手がかりなので、読みだけでは絞りきれない字にいちばん効く。

### 日本語入力としての扱い

10万字をそのまま並べると日本語入力として使えなくなるため、候補は2階層に分けている。

- **KANJIDIC2 収録の 13,108字**（JIS X 0208/0212/0213）… 読み・学年・頻度・画数・部首つき。常に先に出る
- **それ以外の 89,891字**（拡張A〜Jほか）… 常に後ろ。UIでは破線の枠で区別する

### 読み（正式・人名・参考・外国語の4段階）

KANJIDIC2 が読みを持つのは 13,108字だけで、**残り9万字は読みでは一生引けなかった**。
そこで資料にある読みを段に分けて持ち、**正式かどうかを必ず区別**して出している
（作り方は `web/scripts/build-data/readings.mts`）。

| 段 | 出所 | 字数 | UI での出し方 |
| --- | --- | ---: | --- |
| **正式** | KANJIDIC2 の音訓 | 12,356 | 「音」「訓」。大きい字で先頭 |
| **人名** | KANJIDIC2 の `nanori` | 1,350字に付く | 「人名」。小さく下に |
| **参考** | Unihan の `kJapanese` 39,307 ／ 和製漢字の辞典 336 ／ JK 7 ／ zi.tools の音読み 45 ／ 手で足した読み 1 ／ 互換漢字の元の字 921 | 40,617 | 「参考」「参考(和製漢字)」「参考(同じ字 車)」など。小さく下に |
| **外国語** | IRG ワーキングセットの読み（中国語・壮語・韓国語・ベトナム語）のカナ書き写し | 3,641 | 「中国語音 yǐn」のように原語を添えて。小さく下に |
| なし | 資料に読みが無い | 46,385 | 「読みデータなし」 |

**10万字のうち 55.0%（56,614字） が読みで引ける**。

#### 推定はやめた（2026-09-29）

以前は読みの無い字を**推定**で埋めていた（異体字から借用 6,299字・声符（部品）から
推定 42,817字・韓国語音から推定・台湾の閩南語音から推定）。読みで引ける字は97.9%まで
増えたが、声符から推した音が当たるのは6割ほどで、**当たらない読みで字が出てくる**
ほうが困るので外した。いま入っているのは、どれも**資料に書かれている読み**だけ。

- 推定で読めていた約4.9万字（ほとんどが拡張B〜Jの珍しい字）は、読みでは引けなくなった。
  構造・部品・手書き・画数・Unicode 番号では引ける
- **互換漢字（U+F900〜）は推定ではないので残した**。Unicode の正規等価で統合漢字と
  **同じ字**と決まっている（NFC を通すと統合漢字になる）ので、統合漢字の読みをそのまま使う。
  出所は `e:車`＝`参考(同じ字 車)`
- 推定のための元データ（`data-src/readings/zi-variant.tsv`・`taiwan-min.tsv`）は
  取り直しに数時間かかるので、ファイルだけ残してビルドから外してある

#### 参考の読みは件数で切らない

以前は「候補一覧に出す用途なので1字につき4件」で切っていて、**5件め以降の読みは
読みで引けなかった**。いまは切らない。これで Unihan 18.0 の `kJapanese` の読み
104,850件と、和製漢字の辞典の読み3,000件が、**1件残らず読みで引ける**
（切っていたころは kJapanese 2,482件・和製漢字の辞典 332件が落ちていた。
`悪` の「にくむ」、`俣` の「とし」「やす」など）。

- 正式な読みがある字にも、資料にしか無い読み（呉音・古訓・慣用）は**参考として足す**。
  6,795字（悪→コ/ああ/いずくんぞ/にくむ、握→オク/オウ、亜→アク など）
- **読みで引いた候補の並びは「段 → Unicodeに追加された版の順」**。
  段は **常用・人名用（学年のある字）→ KANJIDIC2 の残り → 拡張漢字**の3つで、
  段の中は `1.1 → 3.0 → 3.1 → … → 17.0 → 18.0` の追加順（同じ版の中は符号位置順）。
  版の表は `core/data/age.ts`（UCD の `DerivedAge.txt` から34範囲に畳んだもの）で、
  Kotlin / Swift へは `build:data` が `Age.{kt,swift}` を書き出すので手写しはしない。
  **段を作るのは版順だけでは使えないから**。URO（1.1）だけで20,992字あり、
  符号位置と「よく使う字か」は無関係なので、段が無いと つち→`凷` が、
  ぎょう→`丩` が先頭に来て常用漢字が埋もれる。構造検索の「符号位置順」が
  完全一致→日本の漢字→拡張漢字の段を作っているのと同じ理由。
  この並びは4実装とも同じで、Swift のテストが Web の返す先頭12字と
  1字でも違えば落ちる（`Engine#byReading`）
- **国字（和製漢字）は別の出所で埋める**。国字は中国の字音を持たないので、
  Unihan にも KANJIDIC2 にも読みが無いことが多い（`仦` の「わらわ」など）。
  『和製漢字の辞典2014』（大原望）の3,316項目から、読みのある1,631字・3,000件を取り込んでいる
  （`𠇖`→うかがう、`俧`→たしなみ）。資料にある読みなので段は「参考」で、
  出所は `w`＝`参考(和製漢字)` と出す（`峠` の「びょう」は中峠＝なかびょうの地名読みで、辞典どおり）
  - 見出しに符号位置が書いてある項目（1,783項目）が対象。見出しが画像の項目
    （2014年当時に未符号化だった字）は、項目末尾の漢字林へのリンクが字を指していて
    **総画数が Unihan と合うものだけ**その字として採る（9字。`𬂜` ほだ など）。
    画数が合わないものは同じ字の別の形（榊 の異体など）なので採らない
  - 「「炻器」二字で、「せっき」」のような**熟字訓は採らない**（その字1字の読みではない）
  - `[読み]` が「解説参照」で、見出しに「「はなをかむ」は、国訓」とだけ書いてある字
    （`挗`）は、見出しのほうから読みを取る
- **zi.tools の音読み50,144字・89,491件**も重ねている。Unihan の `kJapanese` と大きく
  重なるが、**1,230字ぶん Unihan に無い読み**を持つ（効→ギョウ・キョウ＝呉音、
  営→ギョウ・ヨウ＝呉音）。これだけが出所になるのは45字。
  取り方は**1字ずつではなく音節ごと**で、`cvt:jp;<子音>;<母音>;*` を447回叩けば
  全件そろう（1回で最大2,000字ぶん返る）。10万回叩く必要はない。
  **呉音・漢音・唐音の区別が24,542字ぶん**付いてくる（Unihan には無い情報）。
  いまは読みだけ使っているが、`data-src/readings/zi-onyomi.tsv` に `読み:時期` の形で残してある
- **JK（IRG国字コレクション）の782字**からも読みを取っている。zi.tools の字典面に
  「「トモ」的合字」「このころ。近来」のように読みを含む説明が付くので、そこから
  かなを取り出す（262字ぶん）。ただし466字は『和製漢字の辞典』と重なるので、
  **これだけが出所になるのは7字**
- **手で足した読み**は `data-src/readings/manual.tsv` に書く（字・読み・メモのタブ区切り）。
  どの資料にも無いが、使う人から足してほしいと言われた読みの置き場所。
  出所は `m`＝`参考(追加)`。いまは `𳍹`（U+33379・拡張J）の「いっさき」1件
- **Unihan は 18.0.0**（2026-07-31）。17.0 から `kJapanese` が28字ぶん直っている
  （`仙` に「せんにん」が増えた、訓がひらがなに揃った、など）

#### 外国語の読み（IRG ワーキングセット）

拡張G以降の字は、IRG（漢字の符号化を審査する国際会議）に各国・地域が提案した字で、
提案の資料に**その字の読みが自分の言語で書き添えてある**。WS2015・WS2017・WS2021・WS2024 の
審査ツール（`https://hc.jsecs.org/irg/<ws>/app/`）から字ごとのページを取り
（`cd web && npm run fetch:irg`、約2万ページ）、Unihan の `kIRG_*Source` で符号位置に結びつける。

| 欄 | 言語 | 例 |
| --- | --- | --- |
| T源 `Optional info`・G源 `Pronunciation` など | 中国語（拼音） | `yǐn` → イン、`zhào` → ジャオ |
| GZ・GZA・GPGLG 源（古壮字の字典） | 壮語 | `caeux` → シャウ、`aep` → アプ |
| KC源 `Pronunciation`（WS2024） | 韓国語 | `익` → イク |
| V源 `Reading` | ベトナム語 | `chuỗi` → チュオイ、`sách` → サック |

- **日本語の読みではない**ので、日本語の読みが1つも無い字にだけ入れる。
  日本語の読みがある字に入れると、日本語で引いたときに関係の無い字が混ざる
- 日本語の音読みに「寄せる」ことはしない（それは推定になる）。**聞こえたとおりに
  カタカナへ書き写すだけ**（`web/scripts/build-data/transcribe.mts`。中国語の e はオ段、
  ベトナム語の v はバ行、など新聞・放送でよく見る書き方に寄せた）。声調は落とす
- UI では必ず原語を添えて「中国語音 yǐn」と出す（出所は `i:zh:yǐn`）。
  読みで引いたときは日本語の読みの字より後ろの段に並ぶ
- 1字に複数の言語が付いていたら、中国語 → 韓国語 → ベトナム語 → 壮語 の順に1つを採る
- WS2015 には読みの欄が無い（英語の備考に、関連する別の字の拼音が出てくるだけ）ので0件。
  WS2024 の字はまだ符号化されていない（Unicode 18.0 に入っていない）ものが大半で、
  Unihan に記号が無い字は結びつけられないので落ちる
- 取れた読みは WS2017 が1,674件（ベトナム語1,006・壮語383・中国語285）、WS2021 が2,222件（ベトナム語1,024・中国語906・壮語292）、WS2024 が1件。読みの付いた字は3,646字で、そのうち日本語の読みが無くて実際に入ったのは **3,641字**。
  韓国語の読みは WS2024 にしか無く、まだ符号化されていないので0件。書き写せなかったのはタイー語の `sl` で始まる2件だけ。
  WS2024 の UK・UTC 源には「かみ (J)」のような**日本語の読み**も25件あるが、どれもまだ符号化されていない
  （符号化されて Unihan に記号が載れば、印を読んで入れられるようにしてある。いまは日本語・広東語の印つきは落としている）

### 読みの入力方法（フリック・ローマ字・Godan）

読みを打つ面は端末のIMEに頼れない（頼ると変換が始まった瞬間に欄ごと持っていかれる）。
かといってフリックしか無いと、**ローマ字に慣れた人が打てない**。3つから選べる。

| | 並び | 打ち方 |
| --- | --- | --- |
| **フリック**（既定） | 12キー（あ行〜わ行＋濁点＋⌫） | 中央=あ、左=い、上=う、右=え、下=お。叩き直しで あ→い→う→え→お |
| **ローマ字** | QWERTY | `tuchi` → つち。パソコンと同じ |
| **Godan** | 左列に母音 A I U E O、中央に K S T N、右に H M Y R W の3列5段 | 子音キーを右に払うと濁音（k→g）、左で半濁音（h→p）、上で拗音の綴り（s→sh・t→ch） |

ローマ字と Godan は**打ちかけを残す**のが要点。`k` の時点ではまだ かな にできないので、
未確定のぶんは読みの欄に色を変えて出し、次のキーと合わせて変換する（`ky` → `kya` → きゃ）。
⌫ は打ちかけがあるうちはそちらから消す。

表は `core/data/romaji.ts`（161件）と `core/data/godan.ts` の1か所にあり、
**Kotlin / Swift へは `build:data` が `Romaji.{kt,swift}`（表＋Godanの配列）を書き出す**。
表がずれると同じローマ字で違うかなが出るので手写しはしない。変換の手続きだけは
3実装に書いてあるので、Swift のテストが TypeScript と同じ答えになるか12件で確かめている
（`[romaji] "kitte" -> きって`）。

設定は共有領域（`katachi.kana`）に置くので、**アプリで選べばシステムキーボードでも同じ面**が出る。

### 画数だけで引く・符号位置（U+XXXX）で引く

読みの面（アプリの「読み」タブ・システムキーボードの読みの面）は、読みのほかに2通りで引ける。

- **画数だけで引く** … 読みを打たずに画数のチップ（`全部` 以外）だけ選ぶと、
  **その画数の字を全部**出す（`30画+` は30画以上）。読めない字でも画数は数えられるので、
  それだけで探し始められる。並びは読みで引いたときと同じ
  **段（学年のある字 → KANJIDIC2 の残り → 拡張漢字）→ 段の中は Unicode に追加された版の順**。
  符号位置順のままだと拡張A（U+3400〜）が統合漢字より前に来て、常用漢字が数百字うしろに沈む。
  ページ送りも読みと同じ（1ページ60字で全件たどれる）。`全部` のまま読みも空なら何も出さない
- **符号位置で引く** … 読みの欄の右、**「消」の左の「U+」**を押すと、かなの面が
  **16進の面**（`1 2 3 A B` / `4 5 6 C D` / `7 8 9 E F` / `0 ⌫`）に替わる。打った16進は
  読みの欄に `U+4E00` のように出て、**番号そのものの字と、その16進で始まる字**が引けた字の行に
  符号位置順で並ぶ（`2B81` → U+2B810〜U+2B81F、`4E0` → 一〜丏）。1桁ずつ打ちながら
  絞っていけるようにするため。引けた字のタップ・長押しは読みで引いた字と同じ
  （タップで部品に・長押しで出力へ）。画数のチップも効く。もう一度「U+」を押すと
  かなの面に戻る（読みも16進も空にする。混ざると何で引いたか分からないので）。
  面の段数・高さはかなの面と同じなので、切り替えてもキーの位置は大きく動かない。
  16進の入力はかなの面の仕組み（フリックの叩き直し・ローマ字の打ちかけ）には通さない
  （A〜F がかなに化ける）

どちらも4実装で同じ答えになる（`core/engine.ts` の `list` ／ Kotlin・Swift の
`Engine#byStrokes`・`Engine#byCode`）。当たり方は `codeHit` の1つの式（文字列を作らず、
符号位置を桁ずらしして打った16進と比べる。10万字を舐めても数ms）で、Swift のテストが
TypeScript の返す先頭の字と件数を突き合わせている（`[strokes-only 5画]`・`[code 2B81]`）。

入力欄（アプリの ⌨ で英数を打ったとき・Web の検索欄）に `U+4E00`・`u+4e00`・`4E00`
（全角の `Ｕ＋４Ｅ００` も可）を打つと、**その1字**が候補に出る（`Engine#search` の mode `code`）。
`U+4E` のような打ちかけは「符号位置: 0件」になる（かたちコードに回すと `+` や `4` を
部品として探して見当違いの0件になるため）。U+ を付けないときは4〜6桁だけを符号位置とみなす。
かたちコード（LR・UD…）には A〜F だけでできたものが無いので、16進とはぶつからない。
一覧（Web の「収録字」）の絞り込みは読みの面と同じく前方一致で並べる。

### 候補の並び順（設定で選べる）

定義は `core/engine.ts` の `SORT_MODES` の1か所で、Kotlin / Swift も同じ値に揃えてある。

**どの並びでも、打ったものと完全一致する字は必ず先頭**に来る（`Engine#score` /
`Engine#codeKey`）。完全一致は

- 操作子つき … 組んだかたちがその字の分解そのもの（`LR日月` → 明）
- 操作子なし … **打った部品だけでできている字**（`木` → 木、`木木` → 林。
  呆(⿱口木)は口が余るので違う）

の2つで、拡張漢字でも先頭に出す（以前は「拡張漢字は必ず後ろ」の下駄のほうが重く、
ぴったりの字が拡張漢字だと数千件の奥に沈んでいた）。違うのは**そのあとの並べ方**だけ。

| | 2字目以降の並び | 向いている場面 |
| --- | --- | --- |
| **符号位置順**（既定） | 符号位置（Unicode）の順にただ並べる | 並びが動かないので、さっき見かけた字を探し直せる |
| **よく使う順** | 学年 → 使用頻度 | ふだんの文章で使う字を出す |
| **かたちが近い順** | **打った部品のほかに余分な部品がいくつあるか**。同じ数のなかは「よく使う順」 | 珍しい字を狙って1字出す |

符号位置順でも**「拡張漢字は日本の漢字の後ろ」は守る**（完全一致 → 日本の漢字 →
拡張漢字の3段に分け、段の中を符号位置で並べる）。段を分けずに符号位置だけで並べると
拡張A（U+3400〜）が統合漢字（U+4E00〜）より前に来て、木を打っただけで 林 の前に
見たこともない字が数百字並ぶ。

「近さ」の物差しは `Engine#leafCount`（再帰的に展開したときの部品の数）。学年や
頻度と違って**拡張漢字9万字にもある**情報なので、10万字を同じ土俵で並べられる。

設定はアプリの設定画面にあり、置き場は**アプリとキーボードで共有する領域**
（`katachi.order`。iOS は App Group、Android は同じ SharedPreferences）。
キーボードに設定画面は無く、アプリで選んだものを読むだけにしてある。

### 候補は全件ページで見られる

絞り込みの**全件**（`total`）を返し、UI は1ページぶんだけ描く（アプリ・Web 200件 /
システムキーボード 60件）。ページを送るたびに10万字を走査し直すと1回数十〜数百ms
かかるので、**直前の絞り込みの全件をエンジンが1件だけ覚えておき**、切り出す位置を
変えるだけで返す（`Engine#search` の offset）。

以前は上位200件で打ち切っていたため、たとえば「木を含む字」13,212件のうち
200件目より後ろの字は**どうやっても出せなかった**。

### キーボードの縦幅（設定で選べる）

小（既定）／中／大の3段階で、**打鍵の面だけ**を縦に広げる（上の帯は打つための
場所ではないので広げない）。倍率と「画面に占めてよい割合」の両方を上げる
（倍率だけ上げても頭打ちに引っかかる）。定義は Kotlin / Swift の `Height`、
呼び名は `core/data/keyboard.ts` の `KEY_HEIGHTS`。

**システムキーボードは3段階とも底上げしてある**（面 168→208dp・画面の
62%→70%、iOS も 320→372pt）。組み立て中のかたち・候補の字も
大きくした（候補 24→28sp / 23→27pt、行の高さ 52→62dp / 46→56pt）。
候補は**見て選ぶ**もので、拡張漢字は点の有無や一画の向きだけが違う字が並ぶため、
小さいと選びようがない。

## 字形の表示（フォント）

端末の標準フォントは拡張B以降を持っていないため、何もしないと候補も部品パレットも
☒ で埋まり「見て選ぶ」という方式そのものが成立しない。
[Plangothic](https://github.com/Fitzgerald-Porthmouth-Koenigsegg/Plangothic_Project)（SIL OFL 1.1）から
**端末が持っていない範囲だけ**を切り出して配っている（URO・拡張A・互換漢字は
Hiragino も Noto も持っているので入れない）。

|             | 方式                                                       | 量                                         |
| ----------- | ---------------------------------------------------------- | ------------------------------------------ |
| Web         | 符号位置1024ごとに124枚へ分割し `unicode-range` で出し分け | 計11.7MB（画面に出た字を含む枚だけ落ちる） |
| アプリ・IME | TTFを同梱し、1字ごとに `fontFamily` を選ぶ                 | 21.7MB（75,292字）                         |

Web は画面に出た字を含むスライスしか取りに行かないので初期ロードは変わらない。
React Native と Android/iOS のネイティブビューには `unicode-range` が無く
`fontFamily` を1つしか指定できないので、同梱のほうは
**符号位置→どちらのフォントか**の範囲表を引いて1字ずつ切り替える。
7.5万字は TrueType の65,535グリフ上限に収まらないため2つに分けてある。

Android は expo-font の静的バンドルで `assets/fonts/` に置かれるので、
**RNアプリとシステムIMEが同じ1部を共有**する（iOSの拡張は自分のバンドルしか
読めないため複製が要る）。生成は `scripts/build-font-app.py` と
`scripts/build-font-slices.py`。元フォント32MBは `.gitignore` 済みで、
切り出したほうをリポジトリに置いている（EAS Build も Vercel も Python を回さないため）。

分解に出てくる「Unicode に字が無い部品」（即の左・鳥の外側など）は、私用領域の字として
データに入っている（→ 分解データの節）。これは BabelStone Han PUA（Arphic Public License）から
部品121個ぶんだけ切り出した `KatachiPUA` で描く（Web 18KB・アプリ 52KB）。
Web は `.kanji` のフォントスタックの先頭に `unicode-range: U+E000-F8FF` で置き、
アプリは `fontFor` が私用領域の字をこのフォントに回す。生成は `scripts/build-font-pua.py`
（元フォント5MBは `assets-archive/fonts/` に置き、`.gitignore` 済み）。

## システムキーボード（IME）

**Android は「設定 > 言語と入力 > 画面キーボード」に登録され、どのアプリの
テキスト欄でも使える**（Simeji などと同じ仕組み）。iOS も「設定 > 一般 >
キーボード」に追加される Keyboard Extension として入っている。

### 構成上のポイント

- **キーボード本体は Kotlin / Swift**。`InputMethodService` にも App Extension にも
  React Native は載せられないので、エンジン（`core/`）を両方へ移植している。
  TypeScript 版と候補の並びまで一致させてある
- **`android/` と `ios/` は prebuild の生成物**（.gitignore 済み）。ネイティブのソースは
  `native/ime/` と `native/targets/keyboard/` に置き、config plugin が毎回コピーする。
  こうしないと `expo prebuild --clean` のたびに消える
- **辞書は tsv**。2.7MB の JSON を起動のたびに構文解析するとキーボードが出るまで
  1〜2秒かかるため。日本語13,108字を先に読んで即検索可能にし、拡張漢字89,891字は
  後から読み足す2段構え
- **iOSのメモリ対策**: 拡張の上限は約60MB。10万字を Swift の String で持つと危ないので、
  読み込んだ UTF-8 を1本の `Data` のまま抱え、各字・各IDSは**バイト範囲(Int32)だけ**を
  覚える。String を作るのは画面に出す数十件だけ（読み込みは全10万字で29ms）
- **フルアクセス**（`RequestsOpenAccess = true`）は履歴・お気に入りをアプリと共有するためだけに
  お願いしている（iOS の拡張が App Group の入れ物を触れる条件）。許可されなければ拡張自身の
  入れ物に落ちて動き続ける。通信は従来どおり一切しない。
  触覚はフルアクセスがある端末でのみ出せる（無いときはキー音のみ）

### Swift 特有の落とし穴

**Swift の `String` は正規等価で比較・ハッシュする**。互換漢字 U+F902（車）と統合漢字
U+8ECA（車）が同じキーとして扱われるため、素直に辞書索引を作ると後から読む拡張漢字が
日本語の字を上書きし、`車` の分解 `⿻亘丨` が消えて `輸`・`輔`・`轍` が候補から落ちる。
索引は先勝ちにして回避している。JS/Kotlin は UTF-16 単位の比較なのでこの問題は起きない。
逆にこの性質を利用して、候補一覧では見た目が同じ互換漢字を1つにまとめている。

## 入力の考え方（スマホでもOSキーボードなしで打てる）

漢字の部品（辶・阝・氵…）はスマホのかなキーボードでは打てないため、**アプリ側にキーボードを持つ**構成にしている。

- **かたち**（常時表示の1行）… 位置関係17種。「左右」「上下」「全かこみ」など。
  IDC文字（⿰⿱⿴…）は端末のフォントによって豆腐(□)になるので、**文字ではなく
  矩形の配置図を描画**している（4実装とも同じ図。定義は `core/ids/operators.ts`）。
  **タブに入れていない**のが要点で、「かたち→部品→部品」と続けて打つのに
  タブを往復させないため
- **部首・偏旁**タブ … かなキーボードでは変換できない偏旁・筆画。先頭のチップは
  **お気に入り**（★に入れてきた字。漢字はそれ自体が部品にもなるので、そのまま
  部品として打てる）で、続く画数チップが zi.tools の「難輸入部件」541件を
  画数ごとに出し分ける。何度も出す字は人によって違うので、固定の部品表ではなく
  自分の★を先頭に置いている
- **読み**タブ … パレットに無い字を読みから引く。かなは**内蔵の面**で打つ
  （システムキーボードと同じ面。端末に日本語キーボードが無くても・OSキーボードを
  出さなくても引ける）。打ち方は**3つから選べる**（設定「読みの入力方法」）。引けた字は**タップで部品として足す／長押しで出力へ**。
  **該当する字は打ち切らない**——「こう」なら4,634字あることを件数で出し、
  ページを送れば全部たどれる。**画数のチップで絞り込める**（10万字ぜんぶが画数を
  持つので拡張漢字にも効く。「こう」＋6画で110字）。件数・ページ送り・画数チップは
  **1行にまとめて**あり、増やしたぶんフリック面が縮まないようにしている。
  読みを打たずに**画数だけ選んでも引ける**。「U+」で**符号位置からも引ける**
  （上の「画数だけで引く・符号位置（U+XXXX）で引く」）
- **手書き**タブ … 読みも部品の見当もつかない字は、枠に書いて引く（下の「手書き検索」）
- **カメラ**タブ … 紙や画面に出てきた字をカメラで読み取る（下の「カメラで読み取る」）

タブは**4つとも同じ幅**にしてある。部首・読み・手書き・カメラは対等な引き方なので、
1つだけが余りを取ると狙う幅がばらばらになって押しにくい。

かたちコードの欄には**端末のIMEを触らせない**。触らせると変換が始まった瞬間に
欄ごと持っていかれ、先に選んだ〈左右〉が消える（React の制御された入力欄と
IMEの変換は相性が悪い）。読みから引きたいときは「読み」タブの内蔵フリックで打つ
（この欄も端末のIMEには触らせない。以前は OS キーボード頼みの TextInput で、
日本語キーボードが無い端末では読みが打てず、出れば画面の下半分を奪っていた）。

WebでOSキーボードが出たとき（読みでさがす）は、欄が隠れないよう画面を縮める
（`interactive-widget` と visualViewport 追従）。アプリがOSキーボードを出すのは
⌨（かたちコードを直接打つ）だけになったので、そのときは iOS は `KeyboardAvoidingView` で
持ち上げる。**Androidは `adjustResize` を指定しても窓が縮まない**（Android 15 からは
画面の端まで描く edge-to-edge が既定で、IMEはアプリの上にかぶさる）ので、
`keyboardDidShow` の高さぶんを下の余白にして自分で逃がす（そのあいだ下端はキーボード
なので、安全域の下の余白は二重に取らない）。⌨のあいだも**かたちの行だけは畳まない**。文字は端末のキーボード、
かたちはタップ、と同時に打てないと〈左右〉を足すたびに往復になる。

### カメラで読み取る（アプリのみ）

読めない字を「見たまま打つ」道具なので、**紙や画面にある字そのもの**を取り込めるなら
部品に分けて組む手間は要らない。撮る → 読み取る → 出てきた漢字をタップで出力へ／
長押しでその字を部品にして検索、という流れ。

読み取りは端末の中だけで完結する（このアプリは通信をしない）。**写真も残さない**——
撮った写真は端末の一時領域にファイルとして置かれるので、読み取りが済んだら
（読めなかったときも）`discardPhoto` でその場で消す。

**撮った向きは EXIF にしか入っていない。** expo-camera は撮影時の向きを画素ではなく
EXIF のタグに書いて返す（`ExpoCameraUtils`: "Record the capture orientation as an EXIF
tag instead of rotating the pixels"）ので、`UIImage(data:)?.cgImage` をそのまま
Vision に渡すと**横倒しの字を読ませることになり、何を撮っても1字も読めない**。
`VNImageRequestHandler(cgImage:orientation:options:)` に `imageOrientation` を
渡して読ませる（Android の ML Kit は `InputImage.fromFilePath` が EXIF を見て回す
ので、この手当ては iOS 側だけ）。

カメラの枠は**面いっぱい**に取る（シャッターは横に並べず枠に重ねる）。写った字が
小さいほど読み取りは当たらないので、枠の小ささはそのまま読み取りの失敗になる。

| | 使うもの | 同梱物 |
| --- | --- | --- |
| iOS | Vision（`VNRecognizeTextRequest` / ja-JP。日本語は iOS 16 から。下限は 16.4） | 増えない |
| Android | ML Kit の日本語モデル**同梱版**（`text-recognition-japanese`） | 約10MB |

Android で未同梱版（`play-services-mlkit-*`）を使うと初回にモデルを落としに行く＝
通信が発生してしまうので、必ず同梱版を使うこと。実装は `native/modules/katachi-ocr`
（`katachi-shared` と同じ、自前の Expo モジュール）。

**システムキーボードにはカメラを載せられない。** iOS のキーボード拡張は
App Extension なのでカメラ権限が下りず、Android の入力方式（Service）は
権限を自分で要求できない（Activity が要る）。そこで4つめのタブは

- **Android** … `ids-kanji-type://camera` でアプリのカメラ面を開く入口
- **iOS** … 「アプリで使えます」と伝えるだけの面

にしてある。組みかけは `Store.savePending` で覚えたまま行くので、アプリで字を
拾って戻ってくれば続きから打てる。

### 手書き検索（Web・アプリ・システムキーボードの4実装すべて）

読みも部品の見当もつかない字は、**枠に書いて引く**。認識は通信なしで端末内だけ
（「何も集めず、どこにも送らない」というプライバシーポリシーを崩さない）。

- パターンは [KanjiVG](https://github.com/KanjiVG/kanjivg)（CC BY-SA 3.0）の筆順つき
  字形 約6,400字から生成する（`npm run build:handwriting`）。SVGパスのままだと13MB
  あるので、**1画を弧長等間隔の8点に間引き、0〜63に量子化した文字列**に畳む
  （1.26MB / gzip 0.8MB）。Webはタブを開いたときに取りに行き、アプリとIMEは同梱する
- 照合は `core/handwriting.ts`。字全体の外接枠で正規化（書く大きさ・位置に
  依存しない）→ 描いた画と参照の画を貪欲に対応づけて1画ずつの距離を合計。**書き順違い・
  逆向きの画・続け書き**（口を2画で書く等。参照側の隣り合う2画をつなげた形とも
  照合する）を小さな加点つきで許す。画数の足切りと重心だけの粗選別を挟むので、
  1回の照合は数ms〜十数ms
- 1画の距離は「**重心を合わせたときの形の違い**」と「**重心そのもののずれ**」に
  分けて測る。素朴に点どうしの距離を測ると2つが混ざり、とくに逆向きに書いた画の
  判定が置き場所に邪魔される（位置がずれていると前向きも逆向きも等しく遠いと出る）

#### 精度は測って決めている

加点の重みは当てずっぽうではない。**KanjiVG の異体字**（楷書体3,488枚・別筆順ほか。
`kanjivg.xml` 本体には1字も入っていないので、辞書から見れば完全に未知）4,959枚を
問題集にして、`npm run bench:handwriting` が実力を測る。

| 条件 | 上位1件 | 上位5件 | 20位まで外す |
| --- | ---: | ---: | ---: |
| そのまま（きれいに書かれた別字形） | 99.7% | 100.0% | 0.0% |
| 崩し重ね（知らない字形 × 乱雑な筆づかい） | 96.9% | 99.4% | 0.4% |

「崩し重ね」は、その異体字にさらに **傾き・縦横比の変化・画ごとの置きずれ・
払いの届かなさ・曲げの直線化・続け書き・筆順の入れ替え** を重ねたもので、
実際の入力にいちばん近い。重みを触ったらこの数字が下がっていないか必ず見ること
（下回るとベンチが落ちる）。

この測り方に変えたことで、それまで見えていなかった負けが見つかって直せた。
崩し重ねの上位1件は **87.5% → 96.9%** に上がっている。効いたのは
「1画の距離を形と置き場所に分ける」（+5.7pt）、
「余った参照の画への罰を軽くする」（+2.8pt。乱雑に書けば画数は合わないのが普通）、
「筆順の加点を画の番号ではなく書き進みの割合で見る」（続け書きで番号がずれるため）。

自己照合の `npm run test:handwriting`（自分のパターンを揺らして引き直す）は
**実力ではなく実装が壊れていないかを見るもの**。両方を残してある。
- 候補は**その字そのものが欲しくて書く**ので、タップは出力（IMEでは相手の欄）へ。
  部品として組みに使いたいときは**長押しでかたちコードに足す**。読みの面が
  「タップで部品」なのと逆なのは、探しているものが違うため
- KanjiVG に無い字（拡張漢字の大半）は手書きでは引けないが、そういう字はそもそも
  誰も筆順を知らない。かたちコードで組んで引く（2方式は補完関係にある）

#### 移植どうしがずれないようにする

エンジンは TypeScript・Kotlin・Swift の3本ある。**同じ問いに同じ候補を同じ順で**
返さないと、同じアプリなのに面によって結果が違うことになる。浮動小数点の扱いは
言語ごとに違うので、次の3点を揃えてある（`core/handwriting.ts` の頭にも書いてある）。

- 参照の点は 0〜63 の**整数のまま**持ち、距離を測るときだけ `1/63` を掛ける
  （float32 で持つと言語ごとに丸めが変わる）
- 長さは `hypot` ではなく `sqrt(dx*dx+dy*dy)`（hypot の精度は処理系依存）
- 並べ替えはスコアが同点のとき**辞書順**で割る（Swift の `sort` は安定ではない）

守れているかは機械で見る。`build:handwriting` が「崩して描いた画」と TypeScript が
返した上位5字を `native/ime/test/handwriting-cases.tsv` に書き出し、
Kotlin・Swift のテストが同じ問題を解いて**1字でも順序が違えば落ちる**。

```bash
cd native/ime/test
# Swift（エンジン本体の検証も兼ねる）
swiftc -O ../../targets/keyboard/{Dict,Engine,Ids,Kana,Handwriting,Age,Romaji}.swift main.swift -o /tmp/ime-test
/tmp/ime-test ../assets .
# Kotlin
kotlinc ../android/java/com/upsee/katachi/ime/Handwriting.kt main.kt -include-runtime -d /tmp/hw-test.jar
java -jar /tmp/hw-test.jar ../assets .
```

#### システムキーボードでの置き場所

**「読み」と同じく面の出し入れ**にしてある（タブではない）。2つは場所を取り合うので
同時には開かず、押した方だけが開く。上の2行（組み立て中・候補）は
どちらを出しても残る。

パターン（1.2MB）は**手書きの面を初めて開いたときにだけ読む**。使わない人に
この読み込みとメモリを払わせないため。読み込みは Android 59ms・iOS 19ms、
1回の照合は Android 6ms・iOS 3ms。iOS は拡張の60MB制限があるので、
全字ぶんを1本のバイト列に詰めて持つ（約3.5MB。1字ずつ配列を作ると小さな確保が
2万個できてしまう）。

### システムキーボードでの打ち方

**このキーボードは読めない漢字を1字入れるための道具**。文章そのものは端末の普段の
キーボードで打ち、読めない字に出くわしたときだけこちらへ切り替える。だから一連の流れは

```
入力方法の切り替え → IdsType → 〈左右〉→ 〈左右〉日 → 〈左右〉日月
  → 候補から「明」を選ぶ（この時点で相手の欄に入る）→ 🌐（普段のキーボードへ）
```

になっていて、画面もその順に並んでいる。

```
[ 履歴  ★  着せ替え                          🌐 ]  ← 道具の帯（打つ場所ではない）
[ (棚) 使った字 / お気に入りの字                    ]
[ 組み立て中: 〈左右〉日月                  ⌫   消 ]
[ 候補: 明 朝 晴 …                                ]  ← 選んだ字はそのまま相手の欄へ
[ かたち: 左右 上下 …                              ]
[ 部首 | 読み | 手書き | カメラ ]  ← 4つとも同じ幅
[ 部品の並び / 読みのフリック面 / 手書きの枠         ]
```

**打鍵の面はスクロールさせない**。読みのフリック面も手書きの枠も指を置いて動かす
場所なので、縦の動きをスクロールに取られると入力そのものが成立しない
（部品パレットだけは数が多いので、その中に自前のスクロールを置く）。
そのため面の高さは「余りを全部もらう」形にしてあり、キーボード自体の高さも
面ごとに変える（読み・手書きのときは高くする。上限は画面の70%／中78%／大84%）。
画面の小さい端末ではフリックのキーと手書きの枠が詰まるだけで、
**下が切れて打てない状態にはならない**。
同じ理由で、案内文だけの行は場所を取らせない。

ただし**打鍵の面は打っている最中に動かさない**。読みの面の断り書きは
打ち始めても引っ込めず、引けた字の行も候補が無いあいだ同じ高さを空けておく
（アプリ・両IMEとも）。1字打つたびに上の行が増えたり減ったりすると、
残りをもらうフリック面がそのぶん伸び縮みして、2字目が隣のキーに入る。
**1行ぶんの高さより、指の位置が変わらないことを取る**。

- **候補を選んだ時点で相手のテキスト欄へ入る**。組み立て中のかたちコードは
  最後までキーボードの中だけに置く（「LR日」のような途中の記号が相手の本文に
  見えないように）が、選んだ字はその場で送る。
  以前は「送る欄」に溜めて「送る」を押したときだけ相手の欄に触っていた——
  押し間違いが本文に残らないようにするため——が、**この道具は1字を入れるために
  呼ばれる**ので、選んだあとにもう一手要ることのほうが高くつく。
  押し間違いは⌫1回で消せる（組み立て中が空なら⌫は相手の欄を1字消す。
  拡張漢字はUTF-16で2つぶんなので、サロゲートペアはまとめて消す）が、
  毎回の余分な1手は消せない
- 以前 Android は組み立て中を composing text として相手の欄に下線つきで出していたが、
  検索欄などでは打っている端からオートコンプリートに巻き込まれた（iOS はもともと
  キーボード内で完結していた）
- **「読み」「手書き」は面の出し入れであってタブではない**。タブにするとかたちの行も
  候補も引っ込んでしまい、部品を1つ読みから出したいだけなのに面ごと往復させられる。
  出しても消しても上の2行はそのまま残る。2つは場所を取り合うので同時には開かない
- **「LR日月 → 明」はキーボードの中だけで組める**。かたちの行で〈左右〉を
  押し、読みの面で「にち」→ 日、「つき」→ 月 とフリックで足せば、上の候補欄に
  明が出る。読みから字を選んだ時点で**読みは空になる**——普通のかな漢字変換と同じで、
  そこで変換は済んでいるため。空になると候補欄も読みの結果から
  組み立て中のかたちの候補へ戻るので、明がそのまま出てくる
- かなの面は12キーフリック。自分が入力方式である以上、読みを打つために他のかな
  キーボードへ移ることはできない（移った時点で組み立て中のコードを持って行けない）。
  途中経過は読みの欄に色を変えて出す（ポップアップは端末によって位置がずれるので
  使わない）。フリックしない人向けに、同じキーの叩き直しで あ→い→う→え→お と
  送るトグルも受ける。**ここは文章を打つ面ではない**ので、面の頭にその断りを1行出している
- **フリックの向きの取り方**（取りこぼしを無くすための3つ）。
  Android の取りこぼしはほとんどが1つめだった
  - 押した瞬間に親へ `requestDisallowInterceptTouchEvent`。Android の打鍵面は
    縦スクロールできる入れ物の中にあるので、断らないと**上下のフリック（う段・お段）を
    スクロールに持っていかれて** `ACTION_CANCEL` で消える
  - 向きは**指がいちばん遠かった位置**で決める（離した瞬間の位置ではない）。
    放るように払うと離すときには戻ってきていることがあり、終点だけ見ると中央（あ段）になる
  - しきい値は**動いた距離**で見る（縦横それぞれではなく）。斜めに払ったときに
    縦横のどちらも届かず中央になる、が無くなる。18dp（キー幅のおよそ1/4）は変えていない
  - 指は**押した指のIDで追う**。速く打って親指が2本重なっても座標が入れ替わらない
- 引けた字は**タップでかたちコードに部品として足す**／**長押しでそのまま送る**
- **往復しても消えない**。かたちコード・打ちかけの読み・かな面の状態を
  打鍵のたびに保存し（`Store.savePending` / `SharedStore.savePending`）、次に開いたとき
  続きから打てる。iOS の拡張は予告なく落とされるので終了時の口には頼らない。
  10分より古い組みかけは捨てる（翌日に知らない字が残っているのは事故に見える）
- 出口は**ほかのキーボードと同じ地球儀キー**（🌐）。押せば次の入力方法へ移り、
  長押しで選択リストが出る（Android は `switchToNextInputMethod()` ＋
  `showInputMethodPicker()`、iOS は `handleInputModeList(from:with:)` がどちらも面倒を
  見る）。以前は「戻る」（↩）という自前のキーだったが、**見慣れた地球儀を押せば
  普段のキーボードへ帰れる**ほうが、この道具だけの決まりを覚えるより速い。
  送った直後だけ色を上げて次の一手を示すが、自動では切り替わらない
  （難しい字が続く語をそのまま組めるように）
- 履歴・お気に入り・着せ替えは打鍵の面と混ざらないよう上端の帯にまとめ、線で区切ってある。
  候補や棚の字を**長押しするとお気に入り**に入る

### 打鍵の触覚

気持ちよさは「指が触れた瞬間に返ること」と「動作ごとに手触りが違うこと」で決まるので、
触覚は押し下げ（`onPressIn` / `ACTION_DOWN` / `.touchDown`）で返し、
キー・確定・削除・連射・切替・成功・該当なしで種類を変えている。
連打で重なる触覚は間引き、⌫長押しの連射は軽い刻みにして音も間引く
（毎回フル強度で返すと手のひらが震えるだけの不快な連続振動になる）。
Android は汎用の Vibrator ではなくキーボード用の触覚定数を使う（端末の設定を
尊重し、VIBRATE 権限も要らない）。強さはアプリの設定画面で オフ／ふつう／強め。

### 着せ替え・設定

着せ替えは7種＋おまかせ（端末のライト/ダーク設定に追従）。定義は
`core/data/themes.ts` の1か所で、Kotlin・Swift へは `build:data` が生成する。
アプリは⚙の設定画面、システムIMEは上端の帯の着せ替えキーで切り替え、選択はそれぞれの
端末側（AsyncStorage / SharedPreferences / UserDefaults）に残る。

設定は入力画面のヘッダーに並べず `src/Settings.tsx` に集約している。
ヘッダーに項目を足すぶんだけ打つ場所が削られるため、増える設定はここへ足す。

### 履歴・お気に入り

確定した字を新しい順に最大60字（`src/history.ts`）。お気に入りは別に持つので
履歴を消しても残る。どちらも端末内にだけ保存する。

**アプリとシステムキーボードで同じ1つを見る**。調べるのはアプリ、打つのはキーボード、
という使い方で入れ物が分かれていると意味がないため、保存先を共有領域に置いてある。

- Android … キーボードはアプリと同じ Service なので `SharedPreferences("katachi")` を直接共有
- iOS … 拡張は別サンドボックスなので App Group（`group.com.upsee.idskanjitype`）の UserDefaults
- アプリ側からその領域を触るのが `modules/katachi-shared`（ローカルの Expo モジュール）。
  1.0.6 までの AsyncStorage の履歴は初回読み込みのときに引き取る

iOS の拡張が App Group を触れるのは**「フルアクセスを許可」が有効なときだけ**なので、
1.0.7 からフルアクセスをお願いしている（用途は履歴の共有だけ。通信は一切しない）。
許可されなければ拡張自身の UserDefaults に落として動き続ける
（キーボードの履歴がアプリと別になるが、機能自体は失われない）。

App Group `group.com.upsee.idskanjitype` は **Apple Developer 側での登録が要る**
（App Store Connect API には App Group を作るリソースが無い）。
Identifiers → App Groups で作り、`com.upsee.idskanjitype` と
`com.upsee.idskanjitype.keyboard` の両方の App ID で App Groups を有効化する。
これが無いと iOS のビルドが署名で落ちる。

### 広告と有料版（土台のみ）

`src/purchases.ts` に権利まわりを集約してあり、アプリ側は `shouldShowAds()` しか
見ない。既定は `ADS_ENABLED = false` で広告枠は描画されない。

**SDK 本体はまだ入っていない。** 広告SDK・課金SDKはどちらもネイティブモジュールで
ビルドし直しが要るうえ、入れると**現在のプライバシーポリシー（何も集めず、どこにも
送らない）と矛盾する**。iOSキーボード拡張の「フルアクセス不要」という訴求とも
関わるので、入れる前に方針を決めること。

## 開発

```bash
cd web    && npm install && npm run dev     # http://localhost:3000
cd native && npm install && npm start       # Expo Go・開発ビルド

npm run typecheck                           # web / native それぞれにある
cd web && npm run test:engine               # エンジンテスト
cd web && npm run test:handwriting          # 手書き照合が壊れていないか(自己照合)
cd web && npm run bench:handwriting         # 手書き照合の実力(異体字での held-out)
cd web && npm run build:data                # 辞書と各言語の生成物を作り直す
cd web && npm run build:handwriting         # 手書きパターン辞書を作り直す
```

手書きの問題集 `web/scripts/testdata/handwriting-variants.tsv` はリポジトリに
置いてある。作り直すときだけ [KanjiVG のリリース](https://github.com/KanjiVG/kanjivg/releases)
から `-all.zip`（22MB・異体字入り）を落として
`npm run build:handwriting-bench -- <zip>` を回す。

`build:data` は `core/kanji-data.json` と `web/public/data/` に加えて、
IME用のtsv辞書と Kotlin/Swift のテーブル（パレット・着せ替え）を書き出す。

生成物を作り直すスクリプト（元データや定義を変えたときだけ）:

| スクリプト                     | 何を作るか                 | 要るもの                      |
| ------------------------------ | -------------------------- | ----------------------------- |
| `data-src/fetch.mjs`           | 元データの取り直し         | —                             |
| `scripts/build-font-app.py`    | アプリ同梱フォント＋範囲表 | fonttools・元フォント         |
| `scripts/build-font-slices.py` | Web用の分割フォント        | fonttools・brotli・元フォント |
| `scripts/build-font-pua.py`    | Unicode に無い部品のフォント | fonttools・brotli・元フォント |
| `scripts/build-icons.py`       | アイコン一式               | pillow                        |

Android のローカルビルドは `cd native && npm run build:android`（動作確認用のAPK）。
JDK 17 は `/opt/homebrew/opt/openjdk@17`、Android SDK は `~/Library/Android/sdk`。

## リリース

バージョンは `native/app.json` の `version` / `buildNumber` / `versionCode` を上げる。

- **Android は EAS のクラウドビルドで出せる**
  （`eas build --platform android --profile production`。署名は `credentials.json`
  経由でこのマシンのアップロード鍵を使う）。ローカルで作りたいときは
  `npm run build:android`
- **iOS はこのマシンで出す**。EAS のクラウドビルドは配布証明書の用意が
  **対話でしか通らない**（`--non-interactive` だと
  「Distribution Certificate is not validated for non-interactive builds」で止まる）。
  下の `xcodebuild` の手順が確実
`runtimeVersion` は appVersion 連動なので、`version` を上げると OTA の系列が変わる
（＝旧ビルドには以後の `eas update` が届かない）。

- **JSだけの変更は OTA で配れる**（`eas update --channel production`）。ネイティブの
  変更（フォント同梱・触覚・IMEのKotlin/Swift・config plugin）は新しいビルドが要る。
  ただし**OTAを受け取れるのは、配信チャンネルを焼き込んだビルドだけ**。
  EAS Build ならチャンネルは自動で入るが、ローカルビルドでは
  `updates.requestHeaders` の `expo-channel-name` を自分で指定しないと入らず、
  アプリの更新リクエストは `expo-channel-name` 不足でサーバーに 400 で弾かれる
  （**1.0.0〜1.0.2 のビルドがこの状態**で、OTAは一切届かない。**1.0.3 以降で有効**）。
  疎通は curl で確かめられる — チャンネル無しなら 400、
  有りかつ配信対象の runtimeVersion なら 200 でマニフェストが返る:

  ```bash
  curl -i https://u.expo.dev/<project-id> \
    -H 'expo-platform: ios' -H 'expo-runtime-version: 1.0.3' \
    -H 'expo-channel-name: production' -H 'accept: multipart/mixed'
  ```
- **Android**: `gradlew bundleRelease` で AAB を作り、`scripts/submit-play.py` で
  internal トラックへ。`withReleaseSigning` プラグインが `store/AuthKey/` の
  アップロード鍵で署名する（鍵が無いとデバッグ署名のままになり Play に弾かれる）。
  提出は edit を作る→上げる→トラックに割り当て→commit の順で、commit するまで
  Play 側に反映されないので途中で失敗しても中途半端にならない。
  **prebuild のあとに `android/build/generated/autolinking` を消してから gradle を
  呼ぶこと**。prebuild は autolinking の結果を package 名を書き換える前に吐くこと
  があり、テンプレートの `com.app` のまま残ると
  `ReactNativeApplicationEntryPoint.java: パッケージcom.appは存在しません` で
  `:app:compileReleaseJavaWithJavac` が落ちる（`scripts/build-android.sh` は対応済み）
- **iOS**: `xcodebuild archive` → `-exportArchive`（`native/ExportOptions.plist`）→
  `xcrun altool --upload-app`。プロファイルは持っていないので
  `-allowProvisioningUpdates` と ASC の APIキーで自動生成させる。
  上げる前に `--validate-app` を通すと、弾かれる原因を先に潰せる

**使う許可の説明文（purpose string）は、雛形のままだと審査を自動で弾かれる。**
使わない許可は文言ごと消す。Apple の自動チェックは
`Allow $(PRODUCT_NAME) to access your microphone` のような既定文を
「中身が無い」と見なす（1.0.9 / build 16 がこれで却下された。expo-camera が
NSMicrophoneUsageDescription を既定で足すせいで、録画しないのにマイクの説明文が
入っていた。`app.json` の expo-camera に `"microphonePermission": false` を
足して外した）。カメラのように実際に使うものは、何のために使い、
撮ったものがどこへ行くのかまで書く。

**アプリレコードだけは App Store Connect の Web UI で作る必要がある**
（API は `apps` の CREATE を許可していない。レコードが無いと `altool` は
`Cannot determine the Apple ID from Bundle ID` で止まる）。
審査への提出と、Play の製品版への昇格も各コンソールでの操作になる。

鍵類は `store/AuthKey/`（.gitignore 済み）。**アップロード鍵を失うと同じアプリを
更新できなくなるので、必ず別途バックアップすること。**

## アイコン

ロゴ（生成りの地に、インディゴとスカイで組んだ字形。中の余白に「漢」が浮かぶ）1枚から、
`scripts/build-icons.py` が配布用アイコンを全部書き出す。マスターは `assets-archive/logo/`。
ブランド色は インディゴ `#4437D1` / スカイ `#34B5FC` / 生成り `#FBFBF9`。

用途ごとにキャンバスに対するロゴの比率を変えている（小さいアイコンほど大きく、
マスクで外周が削られるものほど小さく）。iOS は透過を持てないので生成り地に焼き込み、
Android の前景・モノクロだけ背景を抜いている。ロゴ中央の「漢」の窓は外周と細い隙間で
つながっているため、そのまま背景を抜くと窓まで穴になる。クロージングで隙間だけ塞いでから
抜いているので、ダークなスプラッシュ地でも窓の中の「漢」が沈まない。

## データ出典・ライセンス

分解データは3つの表を優先順位つきで重ねている（`web/scripts/build-data/merge.mts`）。出典の一覧は `data-src/sources.json`。

| 出典                                                                      | 使いどころ                                                                                                                           | ライセンス                                         |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------- |
| [BabelStone IDS](https://www.babelstone.co.uk/CJK/IDS.TXT)（Andrew West） | 土台。Unicode 16.0 の全97,680字。字源タグ(G/H/T/**J**/K/P/V)を持つので日本字体を選べる                                               | 作者が著作権を主張せず、用途・帰属の制限なしと明記 |
| [CHISE IDS Database](https://gitlab.chise.org/CHISE/ids)                  | 穴埋め。BabelStone は Unicode 16.0 準拠で 17.0 の**拡張Jを1字も持たない**。加えて拡張C/Eの末尾18字など他の表に分解が無い20字も埋まる | GPLv2                                              |
| [CJKVI IDS Database](https://github.com/cjkvi/cjkvi-ids)                  | KANJIDIC2 収録字の日本字体。従来の検索結果を変えないため優先している                                                                 | GPLv2                                              |

- 漢字情報（読み・学年・頻度・画数・部首・意味）: [KANJIDIC2](https://www.edrdg.org/wiki/index.php/KANJIDIC_Project)（EDRDG、CC BY-SA 4.0）
- KANJIDIC2 に無い字の読み・画数・IRG の源の記号: [Unihan Database](https://www.unicode.org/reports/tr38/)（Unicode 18.0、Unicode License v3）。`kJapanese` がかな書きの日本語読みを 51,583字ぶん持っている
- 音読み（50,144字）・国字の読み（JK 国字コレクション）: [zi.tools 字統网](https://zi.tools/)。**再配布条件の明示が無い**ので、`data-src/` には置くが配布物への同梱は要確認（`data-src/readings/jk.tsv` `zi-onyomi.tsv` を消せば外れる。推定用だった `taiwan-min.tsv` `zi-variant.tsv` はもう使っていない）
- 外国語の読み（拡張G以降の字に提案国が書き添えた拼音・壮語・韓国語・ベトナム語）: IRG ワーキングセット WS2015/2017/2021/2024 の審査ツール（[hc.jsecs.org/irg](https://hc.jsecs.org/irg/ws2024/app/)、Henry Chan 氏）。IRG の公開審査資料
- 国字（和製漢字）の読み: [『和製漢字の辞典2014』](https://ksbookshelf.com/nozomu-oohara/WaseikanjiJiten/)（大原望）。1,631字ぶん。**著作権表示はあるが再配布条件の明示が無い**ので、`data-src/` には置くが**配布物への同梱は権利者への確認が要る**（同梱しないビルドは `data-src/readings/waseikanji.html` を消せばよい。その字の読みが無くなるだけでビルドは通る）
- 字形表示: [Plangothic](https://github.com/Fitzgerald-Porthmouth-Koenigsegg/Plangothic_Project)（SIL OFL 1.1）
- Unicode に無い部品の字形: [BabelStone Han PUA](https://babelstone.co.uk/Fonts/PUA.html)（Andrew West、Arphic Public License）。分解に出てくる部品121個ぶんだけ切り出して同梱（`ARPHIC-PUBLIC-LICENSE.txt` を添付）
- 手書き検索の筆順パターン: [KanjiVG](https://github.com/KanjiVG/kanjivg)（Ulrich Apel、CC BY-SA 3.0）。SVGのまま同梱せず、ストローク特徴に圧縮して使う（`build:handwriting`）
- 互換漢字（U+F900〜/U+2F800〜）の分解は、正規等価な統合漢字の IDS を NFC 経由で借りている（元データ側に無いため）
- `𫠞`（U+2B81E・Unicode 18.0）の分解 ⿰日欠 と画数8だけ、どの表にもまだ無いので `web/scripts/build-data/supplement.mts` に手で書いている（GPLv2 の2つの表から取ったものではないので、`IDS_SOURCE=babelstone` のビルドにも入る）

`IDS_SOURCE=babelstone npm run build:data` で GPLv2 の2つを外し、BabelStone だけでビルドできる。字数は 102,999 のままだが、拡張J 4,298字の分解データが丸ごと落ちて構造検索に出てこなくなる（BabelStone が Unicode 16.0 準拠のため）。製品化時のライセンス方針は `docs/technical-roadmap.md` 参照。
